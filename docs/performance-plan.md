# แผนพิสูจน์ประสิทธิภาพ

ตัวเลข "เป้าหมาย" คือเป้าออกแบบที่ต้องทดสอบ **ไม่ใช่คำรับประกัน** — รายงานผลจริงแยกเสมอ

## เป้าหมายออกแบบ

| รายการ | เป้าหมาย p95 |
|---|---|
| เทียบเวกเตอร์เมื่อดัชนีพร้อมใน RAM | ≤ 300 ms |
| API ค้นหา (รับไฟล์ครบ → ได้รายการผล) | ≤ 3 วินาที (ภายใต้ภาระที่ระบุ) |
| กดค้นหา → เห็นรูปชุดแรก | ≤ 5 วินาที (เครือข่าย/ขนาดเซลฟีที่ระบุ) |
| รูปย่อใน RAM | วัดแยกจากรูปย่อที่ต้องดึง Drive |
| รูปต้นฉบับ / เริ่ม instance ใหม่ | รายงานค่าจริงแยก ไม่ซ่อนในผล warm-cache |

รายงานเสมอ: **p50, p95, p99, error rate, เวลาในคิว, cache hit rate, จำนวนคำขอ Drive, peak memory**

## ผลที่วัดได้จริงแล้ว (ในสภาพแวดล้อมพัฒนานี้)

### 1) เทียบเวกเตอร์ใน RAM — `scripts/bench_vector_search.py`
วัด **เฉพาะ** ขั้นค้นหาเวกเตอร์ (embed แล้ว + ดัชนีโหลดแล้ว) backend=FAISS, dim=512, 3 ใบหน้า/รูป,
500 iterations, CPU ของ container นี้:

| photos | faces | p50 | p95 | p99 |
|---|---|---|---|---|
| 1,800 | 5,400 | 1.71 ms | 1.86 ms | 2.34 ms |
| 5,000 | 15,000 | 3.29 ms | 3.73 ms | 5.00 ms |
| 10,000 | 30,000 | 5.25 ms | 6.47 ms | 16.2 ms |

→ ต่ำกว่าเป้า 300 ms มาก สำหรับ exact search ขนาดนี้ (ยังไม่ต้องใช้ approximate search)
**ข้อจำกัด:** ไม่รวมถอดรหัสเซลฟี/รันโมเดล/เครือข่าย/ดึง Drive; ขึ้นกับ CPU; ยังไม่วัดพร้อมกันหลายคำค้น

### 2) เวลา embed ด้วยโมเดลจริง (InsightFace buffalo_l, CPU) — วัดจริง
`scripts/accuracy_faces.py` บนภาพจริง: **~436 ms/รูป** บน CPU ของ container นี้
- ผลกระทบต่อ **worker**: 1,800 รูป ≈ 13 นาที, 5,000 รูป ≈ 37 นาที (single-thread, CPU) — พิจารณา batch/GPU
- ผลกระทบต่อ **ค้นหา**: การ embed เซลฟีกินเวลานี้ต่อคำค้น (เป็นตัวครอบเวลา ไม่ใช่การเทียบเวกเตอร์)
  → เป้าหมาย "API ค้นหา p95 ≤ 3s" ต้องเผื่อเวลานี้; พิจารณา GPU/instance แรงขึ้นถ้าจำเป็น
- mock (ข้อ 3) เร็วกว่ามากและ **ไม่สะท้อน** ต้นทุนนี้

### 3) โหลด API เบื้องต้น — Locust, **mock embedder**, uvicorn 1 worker
50 users ทยอย (spawn 10/s, 20s) บนข้อมูลจำลอง 60 รูป:

| endpoint | p50 | p95 | p99 | fail |
|---|---|---|---|---|
| search (รับไฟล์→ผล) | 96 ms | 400 ms | 450 ms | 0% |
| event | 41 ms | 320 ms | 480 ms | 0% |
| preview | 19 ms | 330 ms | 470 ms | 0% |

burst 50 พร้อมกัน: search p50 120 ms, p95 1,800 ms, 0 fail (คิวที่ระดับ ASGI)
**สำคัญ:** ตัวเลขนี้ใช้ **mock** ที่แทบไม่กินเวลา — โมเดลจริงจะครอบเวลาส่วนใหญ่ อย่านำไปอ้างเป็นผลระบบจริง

## ชุดทดสอบที่ต้องรัน (ก่อนสรุปผลจริง)
เครื่องมือ: k6 (`tests/load/k6_search.js`) หรือ Locust (`tests/load/locustfile.py`)

1. 1,800 รูป + จำนวนใบหน้าจริงของชุดทดสอบ
2. 50 users **ทยอยใช้งาน** (ช่วงเวลา/พฤติกรรมชัดเจน) ใช้เซลฟีหลายคน
3. 50 users **ส่งพร้อมกันแบบ burst** — ตรวจการควบคุมคิว/สถานะ busy
4. ชุดขยาย **5,000 รูป** เพื่อหาขอบเขต (ไม่สรุปผ่านโดยไม่มีผลรัน)
5. ดัชนี/รูปย่ออุ่นแล้ว, แคชรูปย่อว่าง, และ **เริ่ม instance ใหม่** (วัด cold start แยก)
6. เพิ่มรูปขณะมีคนค้นหา — ตรวจว่าไม่อ่านดัชนีครึ่งชุด
7. worker หยุดกลางทาง, เรียกซ้ำ, ผู้ถือ lease เก่าส่งผลช้า
8. Drive rate limit/timeout, รูปถูกลบ, สิทธิ์ถูกถอน
9. รูปเดียวหลายคน / คนเดียวหลายรูป / ผลเกินหนึ่งหน้า (>20, >100)
10. ค้นคนที่ไม่มีในงาน, รูปเบลอ, หันข้าง, ใบหน้าเล็ก

## ทดสอบความแม่นยำ (แยกจากโหลด)
- ใช้ภาพจริงมี ground truth และ **ได้รับอนุญาต**
- แยกรูปตั้ง threshold ออกจากรูปทดสอบ
- รายงาน false positive (รูปคนอื่นปน) และ false negative (รูปตัวเองตกหล่น)
- อย่าใช้ unit test เวกเตอร์สังเคราะห์อ้างความแม่นยำจริง (ดู `testing.md`)

## เมื่อไรจึงพิจารณา approximate search
ยังไม่เพิ่มจนกว่าจะมีผลวัดว่า exact search ช้าเกินเป้าที่ขนาดจริง หากเปลี่ยน ต้องวัด **recall ที่หายไป**
เทียบ exact ก่อนใช้งาน
